# Build — Capítulo 02: como materializar o dimensional no mesmo OLTP

> Guia **avançado e detalhado** de construção. Para subir o ambiente pronto, use o [RUNBOOK](./RUNBOOK.md).

## Objetivo

Materializar o star schema do cap. 01 como tabelas reais, dentro do mesmo Postgres do OLTP, num schema `analytics` separado do `public`. O ponto pedagógico é mostrar a convivência (e a tensão) dos dois mundos no mesmo motor — não ainda construir a carga, que é o tema do cap. 03.

## Pré-requisitos de conhecimento

- O star schema do [cap. 01](../01-modelagem-dimensional): fato, dimensões, grão, surrogate keys.
- O schema OLTP e o seeder idempotente do [cap. 00](../00-modelagem-transacional).
- Schemas do PostgreSQL e scripts de inicialização (`/docker-entrypoint-initdb.d`).

## Passo 1 — Reaproveitar a fundação do cap. 00

Não recriamos a origem. O `docker-compose.yml` monta dois scripts de init no container do Postgres, em ordem:

```text
../00-modelagem-transacional/ddl/schema.sql -> 01-oltp.sql   (schema public)
./ddl/analytics.sql                          -> 02-analytics.sql (schema analytics)
```

O seeder também é reutilizado por `build: context: ../00-modelagem-transacional/seed`. Reaproveitar evita divergência: a origem é sempre a mesma do cap. 00.

## Passo 2 — Escrever o DDL do `analytics`

Em [`ddl/analytics.sql`](./ddl/analytics.sql), `CREATE SCHEMA IF NOT EXISTS analytics` e as quatro tabelas do star schema:

- `dim_tempo` — `sk_tempo` (surrogate, `GENERATED BY DEFAULT AS IDENTITY`), `data UNIQUE`, mais `dia/mes/trimestre/ano`.
- `dim_cliente` — `sk_cliente`, a chave natural `cliente_id`, atributos e as colunas de SCD2 (`valido_de`, `valido_ate`, `atual`).
- `dim_produto` — `sk_produto`, `produto_id`, `nome`, `categoria` (desnormalizada de propósito).
- `fct_vendas` — `sk_venda`, as FKs para as surrogate das dimensões, as chaves naturais (`pedido_id`, `item_pedido_id`) para rastreabilidade, e as métricas `quantidade` e `valor_total`.

Use `CREATE TABLE IF NOT EXISTS` para o script ser reexecutável sem erro.

## Passo 3 — Índices nas FKs da fato

```sql
CREATE INDEX IF NOT EXISTS idx_fct_vendas_tempo   ON analytics.fct_vendas (sk_tempo);
CREATE INDEX IF NOT EXISTS idx_fct_vendas_cliente ON analytics.fct_vendas (sk_cliente);
CREATE INDEX IF NOT EXISTS idx_fct_vendas_produto ON analytics.fct_vendas (sk_produto);
```

Consultas analíticas filtram e agrupam pelas dimensões; indexar as FKs da fato acelera os joins do star schema.

## Passo 4 — Deixar a carga para depois (de propósito)

Este capítulo **não** tem job de carga: as tabelas dimensionais sobem vazias. A intenção é separar didaticamente dois passos — (a) a tensão de OLTP e OLAP no mesmo motor, aqui; (b) a carga que resolve surrogate keys, no cap. 03, já com bancos fisicamente separados. Documentar essa escolha evita que pareça uma carga "faltando".

## Validações (definição de pronto)

- [ ] `\dn` lista os schemas `public` e `analytics`.
- [ ] `\dt analytics.*` mostra as quatro tabelas dimensionais.
- [ ] O seeder roda idempotente e popula a origem (`public`).
- [ ] O script de `analytics` é reexecutável (`IF NOT EXISTS`) sem erro.

## Estado final (gabarito para o próximo capítulo)

Um único Postgres hospedando origem e dimensional. O desenho está materializado, mas os recursos físicos são compartilhados — a dor que o [cap. 03](../03-warehouse-dedicado) resolve separando as bases e introduzindo o job `migrate`.
