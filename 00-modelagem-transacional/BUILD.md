# Build — Capítulo 00: como construir a origem transacional

> Guia **avançado e detalhado** de construção. É o passo a passo de implementação — o roteiro que você segue para montar o capítulo do zero e entender cada decisão. Diferente do [RUNBOOK](./RUNBOOK.md), que só executa o que já está pronto, aqui você constrói.

## Objetivo

Modelar e implementar a origem OLTP da NuvemStore: um schema relacional normalizado (3FN) que sustenta o site (escritas rápidas, consistentes, sem redundância) e serve de fonte para todos os capítulos seguintes.

## Pré-requisitos de conhecimento

- Modelo relacional, normalização (1FN/2FN/3FN), chaves primária e estrangeira.
- SQL DDL básico no PostgreSQL.
- Noção de transações ACID (aprofundada no [TECHNICAL.md](./TECHNICAL.md)).

## Estado inicial

Nenhum. Este é o ponto zero da trilha — não há ambiente anterior para recriar.

## Passo 1 — Levantar as entidades a partir do domínio

Antes de escrever DDL, derive as entidades do [COMPANY.md](../COMPANY.md). O núcleo transacional da NuvemStore gira em torno de:

| Entidade | Papel | Por que existe já no cap 00 |
| --- | --- | --- |
| `cliente` | Quem compra | Base da `dim_cliente` (SCD2 no cap 01). |
| `categoria` | Classifica produtos | Normalizada para fora de `produto` (3FN). |
| `produto` | O que é vendido | Base da `dim_produto`. |
| `pedido` | Uma compra | Cabeçalho da venda. |
| `item_pedido` | Linhas do pedido | Resolve o N:N pedido↔produto; é o **grão** do fato de vendas. |
| `pagamento` | Transação financeira | Tem `atualizado_em` — fonte do CDC de fraude (cap 11). |
| `entregador` | Frota própria | Dimensão de entrega. |
| `entrega` | Despacho de um pedido | Ancora os eventos de GPS do streaming (cap 12). |

> A decisão de já modelar `pagamento`, `entrega` e `entregador` não é arbitrária: cada uma atende uma necessidade futura mapeada no COMPANY.md. Modelar a origem pensando no que a plataforma vai exigir adiante é o que diferencia uma plataforma planejada de uma remendada.

## Passo 2 — Escrever o schema normalizado (`ddl/schema.sql`)

Implemente cada tabela com PK, FKs e constraints de integridade. Princípios aplicados:

- **Identidade**: `integer GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY` (padrão moderno, melhor que `serial`).
- **Integridade referencial**: toda FK referencia a PK da tabela pai (`produto.categoria_id → categoria.id`, etc.). Não existe pedido sem cliente válido.
- **Domínios fechados via CHECK**: `pedido.status`, `pagamento.metodo/status`, `entrega.status` usam `CHECK (... IN (...))` para impedir valores inválidos.
- **Regras de negócio como constraint**: `quantidade > 0`, `preco >= 0`, `valor >= 0`.
- **Cardinalidade 1:1 via UNIQUE FK**: `pagamento.pedido_id` e `entrega.pedido_id` são `UNIQUE` — um pedido tem no máximo um pagamento e uma entrega.
- **Cascata controlada**: `item_pedido`, `pagamento`, `entrega` usam `ON DELETE CASCADE` em relação a `pedido` (apagar um pedido remove suas linhas dependentes), mas FKs para tabelas mestre (`produto`, `categoria`, `entregador`) **não** cascateiam.

Verifique a normalização: o nome da categoria mora só em `categoria`, nunca repetido em cada produto. Mudar o nome de uma categoria é um `UPDATE` em uma linha.

## Passo 3 — Construir o seeder idempotente (`seed/seed.py`)

O seeder gera dados sintéticos coerentes com o domínio. Decisões de implementação:

- **Reprodutibilidade**: `Faker.seed(42)` e `random.seed(42)` — toda execução produz o mesmo conjunto.
- **Idempotência**: quando `SEED_RESET=true`, executa `TRUNCATE ... RESTART IDENTITY CASCADE` na ordem correta antes de inserir. Rodar duas vezes não duplica nem deixa lixo.
- **Coerência de estados**: o status do pagamento depende do status do pedido (pedido `entregue` ⇒ pagamento `aprovado`); só há registro de `entrega` para pedidos `enviado`/`entregue`. Isso evita dados que violariam a lógica de negócio.
- **Distribuição realista**: `random.choices` com pesos para que a maioria dos pedidos esteja em estados avançados (entregue), como num e-commerce maduro.
- **Carga em lote**: `executemany` para inserir milhares de linhas sem ida e volta por registro.

Parametrize via ambiente: `SEED_CUSTOMERS`, `SEED_ORDERS`, `SEED_RESET`, `DATABASE_URL`.

## Passo 4 — Empacotar o seeder (`seed/Dockerfile`)

Imagem mínima `python:3.12-slim`, instala `requirements.txt` (psycopg2-binary, faker) e tem `CMD ["python", "seed.py"]`. Esse mesmo contexto de build é reutilizado como serviço `seeder` nos compose dos capítulos 02 e 03 — o seeder vive aqui, na raiz da origem.

## Passo 5 — Diagrama como código (`diagrams/architecture.py`)

Gere o ERD com a lib `diagrams`. O `.py` fica versionado; o `.png` é renderizado localmente (`pip install -r requirements.txt && python architecture.py`) ou pelo CI. Mantenha o arquivo em terminação de linha **LF** — CRLF quebra o parser do Python neste arquivo.

## Validações (definição de pronto)

- [ ] `ddl/schema.sql` cria as 8 tabelas sem erro num Postgres limpo.
- [ ] FKs impedem dados órfãos (tente inserir pedido com `cliente_id` inexistente e confirme o erro).
- [ ] O seeder roda mais de uma vez com `SEED_RESET=true` sem duplicar.
- [ ] As tabelas principais ficam populadas (contagens > 0).
- [ ] `python -m py_compile seed/seed.py diagrams/architecture.py` passa.

## Estado final (gabarito para o próximo capítulo)

Uma origem transacional versionada e reproduzível: schema OLTP + seeder executável + dados de domínio suficientes para alimentar analytics (cap 01–05), CDC (cap 11) e streaming (cap 12). O capítulo 01 usa este modelo como origem conceitual para desenhar o star schema.
