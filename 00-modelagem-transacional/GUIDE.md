## O problema que este capítulo resolve

Antes de qualquer pipeline existir, precisamos de uma fonte de dados. A NuvemStore é um e-commerce com frota própria de entrega, e como toda empresa real, começa com um banco transacional que registra cada venda, cada cliente, cada entrega em tempo real.

O desafio deste capítulo não é tecnológico — é de _design_. Criar um esquema OLTP mal planejado é fácil; os problemas aparecem meses depois, quando uma migração quebra três sistemas, ou quando dados inconsistentes contaminam todos os relatórios.

Este capítulo estabelece o contrato de dados de toda a plataforma: 8 tabelas normalizadas com integridade declarada no banco, não na aplicação. Também constrói um gerador de dados sintéticos determinístico e idempotente.

## Conceitos fundamentais

### Terceira Forma Normal (3NF) e por que importa para OLTP

Um banco OLTP serve para registrar transações: inserir pedido, atualizar pagamento, criar cliente. Para evitar anomalias (inserir um produto sem categoria, deletar a última venda e perder o cliente), separamos entidades em tabelas independentes com relacionamentos explícitos via foreign keys.

3NF significa: cada coluna depende da chave primária, da chave inteira e de nada mais. Na prática: `categoria` não fica dentro de `produto` como coluna de texto — ela vira sua própria tabela, e `produto` referencia `categoria_id`. Isso evita atualizar o nome da categoria em centenas de produtos.

**Exemplo trabalhado — a anomalia que a 3NF evita.** Suponha que guardássemos a categoria como texto dentro de `produto`:

```text
produto_id | nome           | categoria
-----------+----------------+--------------
1          | Fone Bluetooth | Eletronicos
2          | Mouse Gamer    | Eletronicos
3          | Carregador     | Eletronicos
```

A empresa decide renomear "Eletronicos" para "Eletrônicos & Acessórios". Você precisa de um `UPDATE` que toca **toda linha** com aquela categoria — e se uma escapar, o relatório de "receita por categoria" passa a contar duas categorias diferentes para o mesmo grupo. Com a categoria numa tabela própria, o rename é **uma linha** em `categoria`, e todo `produto` que aponta para `categoria_id` reflete a mudança automaticamente. Isso é o que "eliminar redundância" significa na prática.

### GENERATED BY DEFAULT AS IDENTITY vs SERIAL

`SERIAL` cria uma sequence implícita e é o padrão legado do Postgres. `GENERATED BY DEFAULT AS IDENTITY` é o padrão SQL:2003 — mais portável, mais explícito e permite override manual do valor (útil para seeders). Use IDENTITY em projetos novos.

### CHECK constraints e integridade de domínio

Constraints como `CHECK (status IN ('pendente','pago','cancelado','recusado'))` impedem que a aplicação insira estados inválidos. A integridade fica no banco, não espalhada pelo código. Qualquer novo serviço que conectar no banco herda as mesmas regras.

### ON DELETE CASCADE: quando usar e quando evitar

CASCADE é conveniente: deletar um pedido deleta automaticamente seus itens. Mas é perigoso em produção — um DELETE acidental propaga sem aviso. Use CASCADE apenas em relações de composição forte (pedido→item_pedido). Em relações de referência (pedido→cliente), prefira RESTRICT.

**Exemplo trabalhado — a regra de bolso.** Pergunte: *"este filho existe sozinho?"* Um `item_pedido` não faz sentido sem o `pedido` dele → é composição → `ON DELETE CASCADE` (apagar o pedido apaga os itens, correto). Já um `cliente` existe independentemente dos seus pedidos → é referência → `ON DELETE RESTRICT` (o banco te impede de apagar um cliente que ainda tem pedidos, evitando órfãos e perda de histórico). Deixar o default `NO ACTION` em tudo parece seguro, mas só adia o erro: o delete falha em runtime sem você ter declarado a intenção.

### Determinismo e reprodutibilidade no seeder

O seeder usa `Faker.seed(42)` para garantir que execuções repetidas gerem exatamente os mesmos dados. Isso é crucial para validação: se o mart de receita dá R$150.000 na primeira execução, deve dar R$150.000 em toda execução subsequente. Sem seed fixo, cada teste produz números diferentes.

### Idempotência: TRUNCATE vs DELETE

O seeder começa com `TRUNCATE ... RESTART IDENTITY CASCADE`. Isso garante que rodar o seeder duas vezes produz o mesmo resultado. `DELETE` manteria os IDs auto-incrementados avançando; `TRUNCATE ... RESTART IDENTITY` reseta os contadores.

## Etapa 1 — Criar o esquema OLTP normalizado (`ddl/schema.sql`)

### Contexto
Este arquivo é o contrato de dados de toda a plataforma. Todas as tabelas dos capítulos seguintes derivam daqui. Um erro de modelagem aqui propaga para o warehouse, o lake, o lakehouse e o modelo de ML.

### Decisões de design
- *8 tabelas em 3NF*: `cliente`, `categoria`, `produto`, `entregador`, `pedido`, `item_pedido`, `pagamento`, `entrega`. Cada entidade de negócio tem sua própria tabela.
- *Chave de `item_pedido`*: composta `(pedido_id, produto_id)` com UNIQUE, ou surrogate com IDENTITY? Surrogate é mais simples para joins e referências. Chave composta é mais pura em modelagem relacional. Para este projeto, surrogate com IDENTITY.
- *Status como CHECK vs tabela de lookup*: CHECK é mais simples e suficiente para um domínio pequeno e estável. Tabela de lookup é melhor quando status mudam frequentemente ou precisam de metadados (descrição, ordem de exibição).

### O que fazer
Criar as 8 tabelas com: PKs usando `GENERATED BY DEFAULT AS IDENTITY`, FKs explícitas com `REFERENCES`, CHECKs para validar domínios de status, índices em FKs mais consultadas. Usar `CREATE TABLE IF NOT EXISTS` para re-executabilidade.

### ⚠️ Armadilhas
- Esquecer `IF NOT EXISTS` faz o script falhar na segunda execução.
- Não declarar `ON DELETE` explicitamente usa o default `NO ACTION` — que bloqueia deletes silenciosamente. Declare a intenção.
- FKs sem índice no lado referenciante (`item_pedido.produto_id`) causam full table scans em JOINs e deletes cascata.

### 📚 Para se aprofundar
- [PostgreSQL CREATE TABLE](https://www.postgresql.org/docs/current/sql-createtable.html) — referência oficial de constraints e IDENTITY.
- [Use The Index, Luke — Join](https://use-the-index-luke.com/sql/join) — por que FKs precisam de índice.

## Etapa 2 — Construir o seeder determinístico (`seed/seed.py`)

### Contexto
Sem dados, os capítulos seguintes não têm o que processar. O seeder gera 250 clientes, ~1200 pedidos e dados coerentes com as regras de negócio: um pagamento recusado não pode ter entrega concluída, um pedido cancelado não gera receita.

### Decisões de design
- *Faker com seed fixo (42)*: garante reprodutibilidade. Qualquer pessoa que rodar o seeder obtém exatamente os mesmos dados.
- *TRUNCATE no início*: o seeder é idempotente por design — rodar duas vezes produz o mesmo estado. `SEED_RESET=true` controla se o truncate acontece.
- *Ordem de inserção respeita FKs*: cliente antes de pedido, pedido antes de item_pedido, pedido antes de pagamento/entrega.
- *Coerência de status*: se `pedido.status = 'cancelado'`, então `pagamento.status` é 'recusado' e não existe entrega. Essa lógica de derivação simula regras reais de negócio.

### O que fazer
Script Python que: conecta ao Postgres via `psycopg2`, executa TRUNCATE com RESTART IDENTITY, insere dados em ordem FK-safe usando `executemany` para performance, e imprime contagens finais para validação.

### ⚠️ Armadilhas
- `executemany` no psycopg2 é N execuções seriais (não é batch real). Para volume alto, use `execute_values` do `psycopg2.extras`. Para 250 clientes e 1200 pedidos, `executemany` é suficiente.
- `Decimal` do Postgres vira `decimal.Decimal` no Python. Se precisar serializar para JSON ou inserir em DuckDB depois, converta para `float` explicitamente.
- Não fazer `conn.commit()` após os inserts mantém tudo em transação aberta — o seeder parecerá funcionar mas os dados não persistem se o processo morrer.

### 📚 Para se aprofundar
- [Faker Documentation](https://faker.readthedocs.io/) — geradores disponíveis e uso de seeds.
- [psycopg2 — executemany vs execute_values](https://www.psycopg.org/docs/extras.html#fast-exec) — performance de inserção em lote.

## Etapa 3 — Containerizar o seeder (`seed/Dockerfile` e `seed/requirements.txt`)

### Contexto
O seeder precisa rodar de forma isolada e reproduzível. O Dockerfile empacota Python + dependências em uma imagem que pode ser usada no docker-compose dos capítulos seguintes.

### Decisões de design
- *`python:3.12-slim`*: imagem leve (~120MB) em vez da full (~900MB). Suficiente para psycopg2.
- *COPY requirements antes do código*: aproveita cache de layer do Docker. Se o código mudar mas as dependências não, o `pip install` não re-executa.

### O que fazer
`requirements.txt` com `Faker==25.8.0` e `psycopg2-binary==2.9.9`. Dockerfile que copia requirements, instala, copia código, e define `CMD ["python", "seed.py"]`.
